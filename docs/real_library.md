# 真实曲库大盘点（外部有效性第一轮）

> 2026-10-16。**这是本项目第一次在真实音频上跑判定**——此前所有"答案已知"的验证
> 都在**合成语料**上完成。本文件记录：跑法、分布、**独立复核**、暴露的缺陷、以及
> **这份调查不能证明什么**。
>
> 一句话结论：**工具的核心判定在真实素材上站得住**（5/5 例独立复核一致），
> 但它在真实曲库上暴露了 **3 个合成语料永远测不出来的缺陷**，并且给出了一个
> **已关闭功能**（假 Hi-Res 盲检测）的第一个真实误报率数字。

不达标 bad 140   31.2%

**容器分布**

```
44100/PCM_16   206 ｜ 48000/PCM_24  166 ｜ 96000/PCM_24  47
44100/MP3       28 ｜ 88200/PCM_24    1
```

**`bad` 主要由三块构成**（判定文案归类）：

| 文案 | 个数 | 备注 |
|---|---|---|
| 疑似 44.1kHz 升频 | 93 | **全部是 48k/24bit 容器**（内容止于 ~21–22 kHz） |
| 伪 Hi-Res | 20 | 96k/24bit 容器，内容止于 ~21–24 kHz |
| 有损溯源（≈192–256kbps 等） | 83 | 绝大多数是 44.1k/16bit，截止 16–19 kHz |

## 3. 独立复核：不信工具的截止点，自己算一遍

方法：**不看工具的 cutoff**，用独立的 Welch 谱（每声道功率合并，整轨三分位取样）
算出各频段相对通带的电平（`out/_verify_claims.py` 可复算）。

| 文件 | 容器 | 工具判定 | 独立实测（相对通带） | 一致？ |
|---|---|---|---|---|
| `01.LA LA RUN!.flac` | 48k/24 | 疑似 44.1kHz 升频（cut 21.49） | 22–24k **−55.5 dB**；24–30k −63.9 | ✓ 内容确实止于 22k 系 |
| `01. BLACKHOLE.flac` | 96k/24 | 伪 Hi-Res（cut 22.21） | 22–24k −39.9 ｜ 24–30k −44.4 ｜ 30–45k −50.4 | ✓ 高频只是噪声底/镜像 |
| `01. KiLLKiSS.flac` | 96k/24 | 半 Hi-Res（cut 25.06） | 24–30k −42.0 ｜ 30–45k −50.7 | ⚠ **见下方"薄分界"** |
| `雨.flac` | 44.1k/16 | 有损溯源（cut 16.44） | 18–20k −37.1 ｜ 20–22k −42.4 | ✓ 与 ~192kbps 转码一致 |
| `4-Serenade melancolique Op 26.flac` | 88.2k/24 | 真 Hi-Res（cut 44.1） | 30–45k **−15.7 dB**（强能量） | ✓ 真到 44 kHz |

**⚠ 一处"薄分界"要如实记下**：`BLACKHOLE`（伪 Hi-Res）与 `KiLLKiSS`（半 Hi-Res）在
24–30 kHz 的能量只差 **~2 dB**（−44.4 vs −42.0），而判定跨了"bad / warn 两级"。
差别全部压在 `hi_ok = 24.5 kHz` 这一个门限上（cut 22.21 vs 25.06）。
**没有改它**——改它就是拿一份真实曲库去调参，而本项目对"调参迎合数据"的立场写在
`AGENTS.md` §3.4/§3.6。要做对，需要**独立的标注**（哪张唱片确实是升频，由出品方/发行信息确认），
本轮没有。**如实挂账。**

## 4. 真实曲库暴露的缺陷（合成语料测不出来）

### 缺陷 1（**已修**）：`bit_depth_origin` 在 24bit **立体声**上整个失效

- 症状：`codec: only 0-dimensional arrays can be converted to Python scalars`，
  在 88.2k/24bit 立体声上**必现**。
- 根因：`np.bitwise_or.reduce(x)` 默认**只沿 axis 0** 归约；立体声读成 `[n, 2]`
  ⇒ 返回**每声道一个值**（1-D 数组）⇒ `int()` 抛 TypeError ⇒ 被引擎吞成"分析器告警"。
- 后果：**"位深升位（伪 Hi-Res）检测"在最主要的目标形态（24bit 立体声）上永远跑不出来**。
- 为何此前没抓到：`tests/test_codec.py` 的位深用例**全部是单声道**（1-D ⇒ 默认
  axis=0 恰好等于全归约），24bit 分支从没跑到立体声。
- 修：`axis=None` + 3 条立体声回归测试（升位 / 单声道静音 / 真 24bit）。

### 缺陷 2（**已修**）：截断文件"能打开、读数错误、只说一句英文"

- 实测有 **3 个文件**：`01 Electronic Symphony VI/VII ...`（Roland Kayn），
  头部声称 49.1 / 29.7 / 15.1 min，实际只读到 **99.85% / 99.92% / 99.53%**
  就抛 `Internal psf_fseek() failed.`（下载没下全的典型形态：STREAMINFO 先写了，
  数据没跟上）。**注意：`sf.info()` 照旧返回满长帧数**——"能打开"和"读得完"是两件事。
- 后果：用户只看到一句 libsndfile 英文错误，**看不出"文件被截断了"**，
  而结论是拿部分内容算的。
- 修：`basic` 接住读异常，产出 `read_incomplete` / `read_frames` / `read_frames_claimed`，
  并在 `errors` 里写**可读**的"疑似截断（头部声称 N 帧，实读 M 帧 = P%）"。
  **没有**把它判成 `level=error`（可读部分 ≥99.5%，统计有效；判 error 会把整条结论丢掉）——
  这是一个**刻意的取舍**，代价（用户可能没注意）靠文案显眼来补。回归测试给出了
  确定性语料（截断到 70% 的 FLAC）。

### 缺陷 3（**部分修**）：路径超过 Windows MAX_PATH（260）⇒ 文件**静默消失**

- 库里 2 个 `.wav` 全路径 **268 字符**（日文长专辑名 + 长曲名），
  `os.path.isfile` 为 False ⇒ 从清单里被**无声丢掉**，汇总看不出少什么。
  （`.cue.bak` 更长，272 字符。）
- 我构造清单时还踩了**第二个**同类坑：PowerShell `Out-File -Encoding utf8` **带 BOM**，
  而 `--list` 用 `utf-8` 读 ⇒ BOM 留在**第一行**路径上 ⇒ 该文件静默消失
  （实测：6 个文件的清单只分析出 5 个）。
- 修：① `--list` 改 `utf-8-sig`（有 BOM 也能吃）；② CLI 新增
  `_warn_uncollected()`——显式给出的目标若没被收录，**打印出来**（含原因），
  遵守"查不到与没问题必须可区分"。
- **未修**：MAX_PATH 本身（>260 的真实文件仍打不开）。修它要把 `\\?\` 前缀
  贯穿到 `os.walk` / `soundfile`；libsndfile 是否接受 `\\?\` 路径**未验证**
  （我试的形式打不开，但那是路径写错还是 libsndfile 不支持**没分辨**）。如实挂账。

### 缺陷 4（**这是结论，不是缺陷**）：已关闭的假 Hi-Res 盲检测在真实曲库上**没有区分力**

`docs/research.md` §4 写着它的升格前提是"真实曲库误报率可接受"。现在有数字了
（`out/_fakehires_real.py` 可复算，n=48，容器 >48 kHz 的文件）：

```
参照『真』(cutoff ≥24.5k)：n=28 ｜ 候选器报高 2 ｜ 误报率 0.071
参照『假』(cutoff <24.5k)：n=20 ｜ 候选器报高 2 ｜ 检出率 0.100
概率分布：真组 中位 0.412 / p10 0.358 / p90 0.464
          假组 中位 0.418 / p10 0.362 / p90 0.486   ← **几乎完全重合**
```

**两组概率分布重合 ⇒ 这个特征在真实曲库上没有区分力**；0.071 的低误报率是
"它几乎总说不"的副作用（检出率只有 0.10），**不是"准"**。
另有两例误报落在**可证为真**的文件上（`4-Serenade`（30–45k 有 −15.7 dB 强能量）
被判 p=0.569）。
⇒ **维持默认关闭**，且"升格为判据"这条路的**前提被否掉了**，不是"还没做"。

> ⚠ 该测量的"参照"是**本项目自己的截止点判据**，不是第三方标注——所以它的结论
> 不能说成"分类器准确率多少"，只能说到"它**不比截止点强**，且分布与类别无关"。

## 5. 这份调查**不能**证明什么（效力边界）

1. **不是抽样**：n=448 全部来自**一个人**的曲库（日系 ACG / 游戏原声 / Hi-Res 购买为主），
   不代表任何总体。基线率（31% bad）**只属于这份曲库**。
2. **"参照"不独立**：§4 缺陷 4 的分类器评估用的是本项目自己的截止点判据当参照
   （循环性已在文中标注）；§3 的复核才是我自算的独立量。
3. **上游真值未知**：这些文件的**发行方原始母带**无从获取，所以"升频/有损"是
   **从内容反推**（可测量现象），**不是**拿到了证据链。工具自己的输出口径也是这么写的。
4. **两个文件没被分析**：§4 缺陷 3 的 2 个 >260 字符路径仍在结果之外。
5. **判定精度欠账照旧**：`tests/test_props.py` 登记的"9–12 kHz 段偏差可达 15%"，
   在真实素材上**没有重新标定**。

## 6. 复算入口

本文件里的数字由**入库的**探针产出（`packaging/real_library_probe.py`）——
按本项目的规矩，报告里的数字必须能从仓库复算，不能只留一句"我测过"。

```bash
# 全库分析（约 19 min，8 进程）
python -m audiocheck --list out/music_list.txt --jobs 8 \
    --json out/music_all.json --csv out/music_all.csv

# ① §2 的分布总账
python packaging/real_library_probe.py --json out/music_all.json --dist
# ② §4 缺陷 4 的误报率/检出率（约 5 min）
python packaging/real_library_probe.py --json out/music_all.json --fakehires
# ③ §3 的独立 Welch 复核（逐文件）
python packaging/real_library_probe.py --verify "<某个音频文件>"
```

清单的生成（**别用 `Out-File -Encoding utf8`：会写 BOM**）：

```powershell
$p="C:\Users\ASUS\Desktop\Music"
$f = Get-ChildItem -LiteralPath $p -Recurse -File |
     Where-Object { $_.Extension -in '.flac','.mp3','.wav' }
[IO.File]::WriteAllLines("out\music_list.txt", $f.FullName)   # 无 BOM
```

⚠ 该探针**没有** `--strict`：这是**调查**不是门禁。要当门禁，得先有**独立标注**
与**第二个来源**的曲库（见 §5 效力边界）。
