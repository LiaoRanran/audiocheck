## 0. 先把验收口径立起来

这类需求有个陷阱：**"好看"不能用测试证明**。如果验收标准写成"界面变好看了"，
那这份报告只能写"我觉得好看"——那正是本项目一直反对的东西
（把主观判断伪装成结论）。所以本轮验收把标准拆成三类，分开判定：

| 类型 | 判据 | 谁能判 |
|---|---|---|
| **可验证** | 测试 / 基准探针的数字 | 机器 |
| **可复算** | 报告脚本输出的对照度、色阶间距 | 任何人 |
| **主观** | 截图留档 + 参数依据（为什么是这个值） | **用户** |

## 2. 「好看」这件事，本轮实际交付了什么

不能证明"好看"，能证明的是下面四件事——它们合起来叫做
**"每个彩色都有出处，且没有越过可访问性的边界"**：

1. **风格被参数化，不是被手挑**。表面彩度、表面色相阶梯（bg→raised +30°）、
   装饰色阶彩度（0.10→0.18）三个数就是"calm 与 pop"的全部差别。
   想更艳，调这三个数；调完立刻知道哪条判据会红。
2. **每一处彩色都过判据**。文字类 15 条 WCAG（生成时 strict，不达标抛异常）；
   装饰色阶另按"对它会被画上去的底色 ≥3:1"逐档算，三个底色各对应一个真实用法
   （侧边栏底 / 图表底 / 激活导航胶囊底）。
3. **语义没被颜色污染**。合格/有疑/不达标的色相永远固定，装饰色阶只给并列关系用；
   有一条测试专门挡"顺手把 success 改成 deco 里某个好看的颜色"。
4. **截图留档**（`out/shot_vibe_*.png`）：深色 / 浅色 / 樱粉 pop / 多文件对比四张，
   工作区里也各放了一份。**观感请你看过再下结论。**

## 4. 验收中发现的问题（不粉饰，逐条有数字）

| # | 问题 | 数字 | 处置 |
|---|---|---|---|
| 1 | **换肤变慢** | `setStyleSheet` min 100→116 ms、p50 117→122 ms；`apply_theme` 比上轮贵约 10%（仍在 P7 阈值 1500 ms 内） | 已记账进 CHANGELOG 与 §6 欠账表；**未修**（下次改 QSS 前要先跑 A/B） |
| 2 | **浅色主题的 pop 档"更带色"只对一半表面成立** | L=0.995 时请求 C=0.020，sRGB 出来只剩 0.0026——近白色装不下彩度 | 已把测试限定在 bg / surface_hi 两档，并在 docstring 写明这是色域物理边界，不是 bug |
| 3 | **chroma 0.012 时色相定义不良** | a/b 分量与 8 bit 量化噪声同量级，实测抖动 ±10° | calm 的表面色相断言改为 "<15°" 而不是 "=0" |
| 4 | **图表完全不能缩放/平移/打标记** | 全文检索确认：无 `wheelEvent`、无导航工具条，轴范围全部写死 | 差距清单 A1–A5，**本轮未做** |
| 5 | **未重打包验证** | PyInstaller 目录版 280.5 MB 是上一轮的实测，本轮未复测 | 待办 |
| 6 | **ACG 预设的名字是主观的** | 「樱 / 初音 / 霓虹 / 星野」没有任何出处，只是色相的昵称 | 已明确写成"氛围命名而非颜色命名"；种子色本身可验证，昵称不可验证——**这一条要用户裁决好不好** |

## 5. 结论

**有条件通过。**

- 可验证部分：**全部通过**（250 测试 / 两条基准探针 / 对照度报告 / 15 个种子）。
- 可复算部分：**通过**（每个彩色都有令牌与判据出处）。
- 主观部分：**待用户确认**——本轮没有、也不可能用测试证明"好看"。
  产品能承诺的只是：你现在看到的每一个颜色都是算出来的、都在可访问性边界内、
  并且改任何一个都有测试盯着。

**下一轮的主菜不在这份交付里**，而在差距清单的 A1–A5（图表可交互性）
和你新提的三块：材质纹理、字体排版到大师级、内核智能性。
